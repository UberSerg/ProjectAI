# KRK-UX-0001 — Journal V4 смержен и не принят

## Суть

PR #99 влил раскрываемые карточки дня. Владелец, увидев живой журнал, отверг качество: это инженерный лог, а не согласованный Variant 4.

## Как проявляется

Сырые `FILLED`, `Decision #3`, `Order #19`, идентификаторы стратегий, длинный вертикальный список. Текст «детализация недоступна» на старых днях.

## Почему опасно

Merge легко принять за готовность продукта. Пользователь не отличает совет, ордер и исполнение. Доверие к Shadow падает раньше, чем ломается математика.

## Причина

Реализация не совпала с макетом, выбранным 29 октября. Отдельно контракт чтения на main слишком узкий: см. KRK-BUG-0002 и KRK-BUG-0003. Возможен ещё и чужой mount (KRK-BUG-0001): часть скриншотов могла показывать до-V4 дерево.

## Как должно работать

Сжатый аккордеон, русские статусы, группы по инструментам, вторичная диагностика только для OWNER. Даты сигнала, решения и fill разделены. Нет выдуманной причины и нет выдуманного P&L.

## Предлагаемое исправление

Отдельный контракт чтения и UI (снимок: PR #100 и #101), затем приёмка Owner. Не переписывать ledger. Не запускать широкий catch-up ради вёрстки.

## Критерии закрытия

`owner_acceptance: accepted` на конкретном SHA, который реально открыт в браузере после закрытия KRK-BUG-0001. Одного merge #99 недостаточно: он уже случился и карточка остаётся open.

Поля на 2026-11-23: implementation смерженного V4 = implemented в main; приёмка = rejected; runtime показа = reported, не verified.
