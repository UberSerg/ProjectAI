# Ручной журнал операций


## Визуальный ориентир

![Ручной журнал](../../_assets/illustrations/ruchnoy-zhurnal.jpg)

*Append-only операции. Иллюстрация Vault; не скриншот приёмки.*

**aliases:** Manual Ledger  
**Baseline:** `origin/main` `73c2e25e6aed323174b11dea4514946d5897f54b`  
**См.:** [[Персональный портфель]], [[Portfolio Hub]], [[Cost basis]]

## 1. Назначение

Быть единственной финансовой историей личной книги: что человек внёс, купил, продал и какой комиссией это сопровождалось.

## 2. Какую задачу решает

Не даёт экрану или диагностике тихо переписать кэш и позиции. Текущие остатки — проекция журнала, а не второй независимый учёт.

## 3. Как работает простыми словами

После «Начать учёт» каждая операция дописывается в журнал. Исправление идёт через статусы SUPERSEDED или CANCELLED, а не через стирание строки. Средняя себестоимость пересчитывается из этих строк. Комиссия либо сидит внутри сделки, либо проведена отдельной операцией COMMISSION. Один и тот же сбор вторым способом не проводится.

## 4. Архитектура

Таблица источника правды в документе V1: `portfolio.personal_operations` (append-only).  
Проекция: `manual_portfolios.cash_rub`, `manual_positions`.  
Старые ручные write-API после `journal_state=ACTIVE` документ требует держать закрытыми.  
V2 наследует эту модель и сужает её до конкретной книги `{id}`.  
Shadow и Simulator своими журналами личные деньги не ведут. `[GITHUB_VERIFIED]`

Роутер `manual_portfolios.py` на main всё ещё подключён как `/manual-portfolios`. Продуктовый текст V2 говорит, что `/manual-portfolios/primary` снят. Полный список оставшихся ручных маршрутов в этот паспорт не выписывался.

## 5. Поток данных

```text
POST операции выбранной книги
  → строка personal_operations
  → пересчёт проекции
  → load_personal_snapshot
  → NAV, P&L, аналитика
```

Оценка рынком приходит снаружи и не заменяет журнал. См. [[Потоки данных]].

## 6. Что уже реализовано (только подтверждённое)

- Журнал как источник правды и проекция как производное чтение. `[GITHUB_VERIFIED]` текст V1/V2.
- Средневзвешенная себестоимость. `[GITHUB_VERIFIED]`
- Правило комиссии: внутри BUY/SELL **или** отдельный `COMMISSION`. `[GITHUB_VERIFIED]`
- Деньги только `Decimal` / `NUMERIC`. `[GITHUB_VERIFIED]`
- API операций в коллекции personal-portfolios с привязкой к `{id}`. `[GITHUB_VERIFIED]` наличие роутера и описание V2.
- Тарифные профили и счета брокера для **оценки** комиссии: `broker_accounts.py` прямо пишет «No OAuth / execution / secrets — tariff metadata and estimates only». `[GITHUB_VERIFIED]`

## 7. Что частично реализовано

- Облигационная себестоимость: известна только если пользователь указал сумму в рублях. Иначе P&L по позиции пустой. `[GITHUB_VERIFIED]` V2.
- XIRR и полная доходность с внешними денежными потоками в объём V2 не входят.
- PR #86 укрепил порядок обновления контекста портфеля на frontend. Это надёжность загрузки, не новая бухгалтерия. `[GITHUB_VERIFIED]` текст Master Context о составе PR.

## 8. Что пока исследуется

PR B (целостность превью и идемпотентности) и последующий честный realized/unrealized P&L из дорожной карты. Оба пункта в Master Context не переведены в MERGED. `PROPOSED`.

## 9. Технические ограничения

- Нельзя задним числом переписывать уже записанную книгу ради диагностики (инвариант Master Context).
- Нельзя смешивать лоты и штуки так, чтобы превью и журнал расходились в сумме. Целевое поведение PR B это запрещает; факт, что код `73c2e25` всё ещё расходится, этим аудитом не воспроизводился.
- Повтор того же ключа идемпотентности должен вернуть исходную операцию. Конфликт другого тела — отказ. Детали сравнения с текущим тарифом — предмет PR B.
- Валютные догадки (например, считать `3.340000` чем-то иным, чем 3.34 RUB) границами PR B запрещены как подход к исправлению.

## 10. Известные ошибки

Задокументированная постановка PR B, не повторный прогон:

1. Превью может предпочитать штуки, а сервер переводит положительные лоты в штуки через `lot_size`.
2. Смена типа операции сбрасывает дату.
3. Повторное открытие формы может помнить старые поля.
4. Повтор с тем же ключом после смены тарифного профиля может дать 409, потому что комиссия пересчитывается из **текущего** профиля до сравнения отпечатка.

`[GITHUB_VERIFIED]` как текст постановки на main. `runtime_status: unverified`.

## 11. Основные пользовательские сценарии

- Внести депозит, покупку и продажу в активную книгу.
- Увидеть, что комиссия не удвоилась.
- Исправить ошибку новой строкой со статусом отмены или замещения, сохранив историю.
- Открыть черновик, поправить остатки напрямую, затем либо очистить черновик, либо начать учёт.

## 12. Тестирование

Этот аудит тесты не запускал. Документ V1 требует отдельные E2E на `is_test=true`. Наличие таких тестов в дереве поимённо не инвентаризировалось.

## 13. История развития

Журнал появился как расширение Manual Portfolio в дизайне V1 и стал обязательным для ACTIVE в V2. Технический релиз V1.0 в CHANGELOG описывает портфельную аналитику общими словами и не выделяет отдельную главу «ручной журнал». Точная дата первого merge журнала в этот паспорт не выводилась из `git log` пофайлово.

## 14. Потенциальное развитие

PR B, затем (по дорожной карте, отдельными этапами) себестоимость лотов, реализованный и нереализованный P&L, XIRR. Импорт брокерского отчёта в журнал не планируется принятым решением 2026-11-19.
